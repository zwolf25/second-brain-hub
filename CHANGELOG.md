## Archive: v2 AI Search (implemented in v2, removed in v3)

**What it was:** a toggle in the topbar that switched from keyword search to a natural-language question box, backed by two on-device models via `candle` — `all-MiniLM-L6-v2` for embedding/retrieval and `Qwen2-0.5B-Instruct` (Q4_0 GGUF) for answer synthesis, fused via Reciprocal Rank Fusion with the existing tantivy keyword index. Fully implemented, shipped, and put through substantial live-testing hardening (§11 #1–2, #4–11 are all from this era).

**Why it was removed:** the answer-synthesis model was too weak for reliable production use. Real, evidenced findings from live testing (kept here as the record of *why*, not as current-state documentation):
- On specific/technical queries, retrieval itself struggled — a documented gap where dense identifier-heavy content (e.g. a feature-flag reference list) embedded too weakly to surface, even after the RRF hybrid-retrieval fix narrowed it (rank ~13, not rank 1).
- Even with retrieval working, the 0.5B generation model periodically produced degenerate output — fabricating a whole new conversation turn as plain text past its real answer, or echoing the question back verbatim instead of answering. Multiple rounds of guardrails shipped (repeat-penalty, stop-token + plain-text-marker truncation, exact-echo detection, single-threaded determinism fix) and each helped, but none addressed the root cause: a model this small has a real capability ceiling on a laptop CPU. Bumping to 1.5B-Instruct was tested and didn't meaningfully help (same retrieval-starved context, just slower).
- Conclusion: continuing to patch symptom-by-symptom wasn't converging on "reliably good," because the ceiling was the model's capability, not a fixable bug. Decision: remove AI Search entirely and redirect the effort into making keyword search itself smarter (exact-match + phrase-match boosting, stopword handling — see §4) — a more modest but much more reliable improvement, and one every query benefits from instead of only the subset of users who'd opt into a flaky AI mode.

**What's gone:** `llm.rs` (deleted), the `chat_availability`/`enable_chat`/`related_docs`/`write_answer` commands, the `embedding_model`/`chunk_embeddings` app state, the AI Search UI toggle and chat panel, and the `candle-core`/`candle-nn`/`candle-transformers`/`tokenizers`/`reqwest`/`rayon`/`sysinfo` dependencies (all were only used by this feature). This also dropped the ~440MB one-time model download and shrank the build.

Full implementation detail (chunking, RRF math, the TLS/Zscaler download fix, the model-size ladder, every live-testing bug and fix) is preserved in this file's git history if it's ever useful again — not worth keeping inline now that the code itself is gone.

### Bugs and lessons from that era (formerly ARCHITECTURE §11)

1. **Download hang risk:** `reqwest::blocking::get` (the free function) has no timeout. A real network failure would hang the download — and the UI waiting on it — forever with no error. **Fixed:** build an explicit `reqwest::blocking::Client` with a 15s connect timeout and 20-minute overall timeout.
2. **UI looked frozen during the compute-only phase:** once a model finishes downloading, `enable_chat` still has real work left (loading the model, embedding ~1132 chunks) with no download-progress bytes to report — the progress bar/label just sat stale, indistinguishable from actually being stuck. **Fixed:** added a `chat-status` event emitted before each compute phase, decoupled from the byte-progress `model-download-progress` event.
4. **Debug-build slowness looked like a hang:** see §8's dev-mode note — a legitimate ~minutes-long debug-profile compute phase was initially mistaken for a stuck process. Diagnosed via `ps`/`lsof` (99% CPU, zero open network connections — ruled out a network hang, pointed at unoptimized compute instead) before concluding it needed `--release`, not a code fix.
5. **Mutex held across expensive computation → concurrent calls block, reads as "stuck loading forever":** `enable_chat`, `related_docs`, and `write_answer` all locked `embedding_model`/`chunk_embeddings` and held the lock for the *entire* duration of the embedding computation (`build_chunk_embeddings`, `top_related`'s `embed()` call), not just the brief moment of reading the value out. A second call touching the same lock (e.g. re-selecting AI Search, or `chat_availability` firing while `enable_chat` was still running) blocked waiting on it — with a 27-second `enable_chat` call observed live, this read as a permanent hang rather than a normal wait. **Fixed:** wrapped both fields in `Arc` (`Mutex<Option<Arc<EmbeddingModel>>>`, `Mutex<Arc<Vec<ChunkEmbedding>>>`) so every call site clones the `Arc` and drops the lock immediately, before doing any real work — the lock is now only ever held for a pointer clone, never across computation. General lesson for this codebase: never hold a `Mutex` guard across an `await`-equivalent or a slow synchronous call — clone what you need out from under the lock first.
6. **Real UI freeze during embedding computation, silently swallowing every loading-indicator design tried:** three different loading-UI implementations (a progress bar nested in the panel, a `position: fixed` overlay, a spinner nested in the panel) all failed identically — the indicator's `classList` change demonstrably executed (confirmed via `console.log` and `tracing::info!` on both sides, ruling out a JS/Rust logic bug) but nothing ever appeared on screen. Root cause, per Zac's own diagnosis: the CPU-heavy embedding computation starves the webview's render thread badly enough that a DOM mutation made *immediately before* the blocking `invoke()` call never gets painted — the freeze hits before the browser's next paint cycle fires. This wasn't a CSS/layout bug at all; every DOM-structure change made while chasing it was solving a non-problem. **Fixed:** force a real paint to commit before starting the heavy work — `await new Promise(r => requestAnimationFrame(() => requestAnimationFrame(r)))` between showing the loading state and calling `invoke("enable_chat")`. Double-rAF (not a single rAF, not `setTimeout`) is the standard technique for "block until the browser has definitely painted the current frame." General lesson: if a DOM update provably runs (via logging) but never renders, suspect a starved render thread before suspecting the DOM/CSS — and diagnose via devtools console + `tracing`, not by redesigning the markup.
8. **Automatic-generation redesign fired the heavy chat model on every typing pause, not just on submit:** the first cut of the "automatic answer" UI (§8) chained `write_answer` straight off the same 200ms debounce as extractive search. That's fine for extractive (cheap, near-instant) but generation is CPU-heavy enough to freeze the render thread for its full duration (same class of issue as #6 above) — so it fired, and froze the UI, on every natural mid-sentence typing pause, not just when the user finished asking. Caught live: Zac reported the app locking up after typing only "what " of a longer question. **Fixed:** split the two triggers — extractive search (`related_docs`) stays on the debounce; generation (`write_answer`) only fires on explicit submit (Enter key or the Ask button). General lesson: "automatic" and "on every debounce tick" aren't the same thing once one of the two chained operations is expensive — a debounce that's safe for a cheap operation isn't automatically safe for a heavy one chained after it.
9. **`sysinfo::System::available_memory()` returns a flat `0` on macOS**, confirmed via a live diagnostic test on an 18GB Mac using ~15GB (`total_memory` correct at 19.33GB, `available_memory` exactly `0`, `free_memory` a real-but-misleadingly-low 0.22GB). This is a known sysinfo/macOS gap — it undercounts reclaimable inactive/purgeable pages that `vm_stat` and Activity Monitor both count as available. The low-RAM safety net (§8) built on `available_memory()` therefore fired on *every* query regardless of actual headroom. Caught live: Zac got "Not enough free memory" on a normal, otherwise-idle Mac. **Fixed:** use `total_memory() - used_memory()` instead — confirmed against `vm_stat` to track real availability (~4.16GB on this machine), and well-supported cross-platform. General lesson: don't trust a systems-info crate's cross-platform API surface uniformly — verify the specific method against ground truth (`vm_stat`, Activity Monitor, Task Manager) on each target OS before gating real functionality on it.
10. **Small model drifts into a fabricated new conversation turn, written as plain text, not caught by stopping at the `<|im_end|>`/`<|im_start|>` control tokens:** live repro on a real weak-retrieval query ("How do I enable rate validation?") showed `generate_answer` producing a real, coherent answer and then continuing to generate past it — literally decoding the text `"\n\nQuestion: <invented question>"` — because the model never actually sampled the `<|im_start|>` token for it, just wrote the string "Question:" as ordinary vocabulary. Adding `<|im_start|>` as an additional stop-token condition (kept as cheap insurance) did **not** fix this, since token-level stopping can't catch a drift expressed as plain decoded text. **Fixed:** `truncate_at_fabricated_turn` post-processes the decoded string, cutting at the first `\nQuestion:`/`\nUser:`/`\nQ:` marker. Also separately observed on other weak-retrieval queries: the model sometimes just echoes the question verbatim instead of answering or declining — caught with a narrow exact-normalized-match check (not general low-quality-answer detection) that swaps in a plain "couldn't generate a grounded answer" message. Both are small-model-capability limits, not code bugs to eliminate entirely — the fixes bound the damage a user sees, they don't make the 0.5B model reliably good at every query.
11. **Generation wasn't actually reproducible across app launches — the real root cause behind #10's variety of symptoms:** after shipping #10's fixes, Zac hit a *third*, differently-shaped variant of the same underlying problem on the exact same query ("Questions: How do you enable rate validation?" — no leading newline, plural "Questions", so neither the truncation markers nor the echo-normalize check caught it). Attempting to repro it against the real vault gave a *third, different-again* answer on each of several separate process runs — for the identical query, identical retrieved context, identical fixed sampling seed, and pure greedy (`ArgMax`) decoding, which should be fully deterministic. Root cause: with the thread-pool cap at >1 thread, rayon's parallel float reduction inside gemm's matmul doesn't guarantee a fixed summation order across runs (a known rayon+floating-point caveat — work-stealing means which worker's partial sum lands where isn't pinned to a static schedule), so tiny rounding differences at some token step tip a greedy argmax pick a different way, and the entire rest of the decode diverges from there (small-model decoding is chaotic in this sense). **Fixed:** dropped the thread cap from 2 to 1 (§8) — confirmed via a repeated same-process test (identical query run twice back to back) that 1-thread generation is now byte-for-byte deterministic. This is the more fundamental fix underneath #10's point patches: those patches still matter for genuinely bad model outputs, but before this fix, *which* bad (or good) output you got for a given query was itself random per launch, which made every prior fix impossible to verify with real confidence — a repro that "worked" once could just as easily have been luck. General lesson for this codebase: never assume a fixed-seed, argmax/greedy decode path is deterministic just because the sampler has no randomness in it — the matmul underneath can still introduce real nondeterminism once more than one thread is involved, and that's worth checking explicitly (rerun the same input twice) before trusting any single repro as conclusive.
