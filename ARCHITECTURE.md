# Architecture — Second Brain Hub

Local desktop app that indexes the shared SC PM "Second Brain" wiki vault (OneDrive) and gives fast fuzzy full-text search over it. Runs entirely on the collaborator's machine — no server, no cloud calls, no API tokens. Written for a small internal team, not a public product; scope decisions below favor simplicity over generality.

(Product name is "Second Brain Hub"; the underlying project folder, npm package, and Rust crate/binary are still named `second-brain-search` — internal plumbing, not user-visible, left as-is rather than doing a full rename.)

Status: shipping; current version in `package.json`. Keyword search, Raw/Inbox/shared-raw badges, an in-app markdown viewer/editor and default-`.md` handler, a Skills catalog, the Neural Map, Settings, the auto-updater and Transcripts all work on Mac; Windows builds ship but are largely unverified (§12). The v2 local chat was removed in v3 (§8). Version-by-version history lives in `CHANGELOG.md`; this file describes the current state.

## 1. Stack

- **Tauri 2** (Rust backend + OS-native webview). Chosen over Electron for installer size (~10-20MB vs ~150-200MB) and idle resource footprint — this machine had no Rust toolchain when the project started, installed via `rustup`.
- **tantivy** — embedded Lucene/BM25-style full-text engine, runs in-process, no server. Gives genuine fuzzy (edit-distance) search, which tantivy's default `QueryParser` does not do on its own — the query layer builds `FuzzyTermQuery` clauses manually, alongside exact-term and phrase clauses (see §4).
- **Plain HTML/CSS/JS frontend**, no framework. The UI is a search box, a results list, topbar heads-up badges, and a Skills/Map/Settings trio of full-page views sharing one header-+-scrolling-list pattern (§14) — a framework buys nothing at this scope.
- `tracing` + `tracing-appender` for structured local logging; `notify` + `notify-debouncer-mini` for vault/raw/inbox file-watching; `walkdir` for directory traversal; `serde_yaml` for frontmatter parsing; `anyhow` for error plumbing.

## 2. Module layout (`src-tauri/src/`)

| File | Responsibility |
|---|---|
| `config.rs` | `AppConfig` (`vault_path`, `raw_path`, `inbox_path`), load/save as plain JSON in `app_config_dir()`, path validation, OneDrive path auto-detection (shared `autodetect_second_brain_root` helper, reused for all three paths) |
| `frontmatter.rs` | Splits `---`-delimited YAML frontmatter from markdown body (hand-rolled, not a crate — simple enough and avoids depending on an unfamiliar crate's exact API), extracts title (first `# ` heading, fallback filename), strips `[[wikilink]]` brackets for clean display |
| `index.rs` | tantivy schema definition, full vault walk + rebuild, index open. Includes a fuzzy-search round-trip test |
| `search.rs` | Query construction (title/topics/body — exact-term, fuzzy, and phrase clauses, stopword-filtered; title and topics boosted highest), snippet generation, `SearchResult` shape returned to the frontend. Includes ranking-quality tests |
| `counts.rs` | `count_unprocessed_raw` (missing `<!-- wiki-processed -->` marker) and `count_inbox_items` (`*.share.md` count) for the topbar heads-up badges. Includes a fixture-based unit test |
| `watcher.rs` | Debounced (400ms) filesystem watch, triggers a full reindex (vault) or recount (raw/inbox) on any change — generic over which folder it's watching |
| `logging.rs` | Rolling daily log file, 7-day retention pruning, panic hook that logs crashes to the same file |
| `skills.rs` | Walks the shared vault's `skills-repo` for every `SKILL.md`, parses name/description/mtime for the Skills catalog (§14) |
| `lib.rs` | Tauri app wiring: `AppState`, command registration, startup sequence |

## 3. Indexing pipeline

On startup (if a vault is configured) and on every debounced file-watcher event, `index::rebuild()` does a **full re-walk-and-reindex** — deletes the on-disk tantivy index directory and rebuilds it from scratch by walking every `.md` file in the vault root. This is simpler than incremental per-file diffing and, at real-world scale completes in well under a second. Measured 2026-11-01 on the real shared vault: 218 docs in 594 ms (`cargo test real_vault_rebuild_time -- --ignored --nocapture`); every reindex now logs `indexed N docs from <path> in M ms`. Revisit incremental indexing only if that log line shows seconds.

**tantivy schema:** `path` (STRING, STORED — canonical doc id, also the click-through target), `title` (TEXT, STORED), `body` (TEXT, STORED, wikilink brackets stripped), `topics` (TEXT, STORED, from frontmatter, wikilink brackets stripped), `updated` (STRING, STORED, from frontmatter).

**Frontmatter handling:** every wiki file's frontmatter has `type`, `topics` (a list), `created`, `updated` — no `title` field, confirmed by reading real files, hence the first-`# `-heading fallback. OneDrive transient files (filenames starting `~$`) are skipped; unreadable files are skipped rather than aborting the whole rebuild.

**Scope note:** this app indexes the **shared vault only**. Zac's separate personal ZacAI vault and its `second-brain/` pointer-stub subfolder are explicitly out of scope — dropped early to keep indexing/onboarding simple (no stub-dedup logic, no vault-source filter UI).

## 4. Search (Search tab)

Query flow: debounced (~200ms) keystroke in the frontend → `search_vault` Tauri command → `search::search()`:
1. Tokenize the query on whitespace, lowercase each token.
2. Filter out stopwords (a small hardcoded list — "how"/"do"/"i"/"the"/etc.) *for clause-building purposes only* — the tantivy fields themselves still index stopwords normally, so exact/phrase matching against them still works. Falls back to the unfiltered token list if the whole query happens to be nothing but stopwords, so a degenerate query still searches on something. This matters more post-v2 (§8): with AI Search gone, people type the same natural-language questions ("how do I enable rate validation") into keyword search that they used to type into the AI box, and unfiltered fuzzy matching on "how"/"do"/"i" was diluting ranking exactly for that query shape.
3. For each remaining (significant) token, build **two** `Should` clauses per field (`title` boosted 3.0×/2.0×, `topics` 2.0×/1.5×, `body` 1.5×/unboosted) — an exact non-fuzzy `TermQuery` at the higher boost, and a `FuzzyTermQuery` (edit distance 1 for short tokens ≤5 chars, 2 for longer ones) at the lower boost. Two clauses per field, not one, because the old fuzzy-only version scored a precise match and a same-distance typo match identically — nothing ranked a real hit above a near-miss.
4. If the query has 2+ tokens, add one more heavily-boosted (5.0×) `PhraseQuery` clause against `body` for the literal token sequence — a page containing the exact multi-word phrase (a distinctive feature name, say) jumps above pages that only match scattered individual terms.
5. All clauses OR'd together (`Occur::Should`) in a `BooleanQuery`, `TopDocs::with_limit(30)`.
6. Generate highlighted snippets via tantivy's `SnippetGenerator` on the `body` field; falls back to a plain 220-char excerpt if snippet generation yields nothing.

Tested in `search.rs` itself: `exact_match_outranks_fuzzy_typo_match` and `stopword_heavy_natural_language_query_still_surfaces_the_right_doc`. `index.rs`'s original `rebuild_and_fuzzy_search_round_trip` still covers the index-rebuild path and basic typo tolerance.

**Wiki families (0.11.0):** `graph::families` maps each hub (a wiki with `## Child wikis`) to its existing children. The search page's family select (`get_families`) passes `family` to `search_vault` and `recent_wikis`; `search::search` then fetches 1000 candidates and keeps the first 30 whose file stem is in the family, because filtering after a top-30 cut would leave almost nothing. **New since last visit:** `localStorage.lastSeenAt` is read once at launch and re-stamped, so "new" means updated after the previous launch's start; `search::recent` returns `new_count` (all docs, not just the 5 shown) and the page badges rows with `updated > lastSeenAt`. First launch has no baseline, so nothing is new.

**Opening a result:** double-click (not single-click — deliberate, so scrolling/scanning results doesn't accidentally open files; a "Double-click a result to open the file" hint is shown under the search box). Calls `tauri-plugin-opener`'s `openPath` directly from the frontend (`window.__TAURI__.opener` global). See §11 for a real permission bug this hit and how it was fixed.

## 5. Onboarding & config

First run: no `config.json` in `app_config_dir()` (or no `vault_path` in it) → onboarding screen. `autodetect_vault` command probes for a OneDrive folder under `~/Library/CloudStorage` (macOS) or the user's home directory (Windows-style layout) containing `SVC-Product_Management - Second Brain/wikis` with at least one `.md` file. If found, the user gets a one-click "Use detected folder" button; otherwise a native folder-picker (`tauri-plugin-dialog`) is the fallback — every collaborator's OneDrive path differs by username/OS, so this can never be hardcoded.

Config persists as plain `serde_json`-written JSON — no config-management plugin, three fields doesn't warrant one. As of §6 below, `AppConfig` actually has three path fields (`vault_path`, `raw_path`, `inbox_path`), so "three fields doesn't warrant a plugin" now describes the real shape, not just the vault.

## 6. Shared header, ☰ page menu, heads-up badges (omnipresent)

**Shared header (0.12.0):** one `#app-header` above every page except the viewer (own Back) and first-run Settings (no vault yet; `hasVault` via `updateBackButtonVisibility`). Left to right: ☰, page title (`VIEW_TITLES`, set in `syncHeader`), index status (search page only), then 📥 inbox, raw, 🌐 shared raw, Claude, Refresh as icon-only buttons with `data-tooltip`. Icons are inline Lucide SVG (`.ico`). ☰ opens `#nav-menu` (Search, Transcripts, Skills, Map, Settings; ⌘/Ctrl 1-4 and ⌘, shortcuts). Plugin drift shows as a red count on the Skills row and a dot on ☰ (`renderSkillsBadge`); Transcripts hides with `hide_transcripts_page`. The old per-page "← Back" buttons are gone; page-specific controls (map stats, transcript filters) stay in a slim per-page `.topbar`. The text below describes the badges and predates the layout change; the emoji it names are now the icons above.

Four always-visible controls in the topbar (not inside the search panel, so they're always on-screen): a 📄 badge for unprocessed raw notes (`wiki-builder`'s job), a 📥 badge for pending inbox items (`inbox-review`'s job), a 🌐 badge for the total unprocessed raw-file count across the *whole shared* Second Brain vault (added in v3 — see below), and a Claude-icon button that opens a blank new Claude Desktop session (`claude://code/new`, no `q` param — nothing pre-filled, unlike the badges below). The Claude icon itself is copied from the locally-installed `/Applications/Claude.app` bundle (`ion-dist/images/claude_app_icon.png`) rather than recreated, so it matches the real app icon exactly.

Clicking the 📄/📥 badges jumps straight into Claude Desktop with the matching slash command pre-filled. The 🌐 shared-raw badge is different on purpose: it's **purely informational**, a "freshness" signal for the wikis a collaborator is reading, not an action they can take (they didn't submit those files, someone else on the team did). Clicking it just reveals the shared `raw/` folder in Finder/Explorer (`revealItemInDir`) instead of launching a Claude command.

**Shared-raw badge, v3 addition:** reuses the same counting logic (`counts::count_unprocessed_raw` — folder-agnostic, marker-based) and the same 4-slot settings pattern as the other three paths, just pointed at a different folder: `config::autodetect_shared_raw()` is `autodetect_second_brain_root()?.join("raw")` (the shared vault's own `raw/`, not `wiki-builder`'s personal path used by `autodetect_raw`). No new counting logic was needed — the existing marker-based function already works against any raw folder, including this one. **Deliberately not per-user-attributed:** the raw files carry no author/submitter frontmatter field today, so "unprocessed files *you* added" isn't buildable without also changing the note-writing skills outside this repo — shipped as a total-across-everyone count instead, which is still a genuine freshness signal without that dependency.

**Paths & auto-detect:** `config::autodetect_second_brain_root()` is the OneDrive-probing logic originally written just for the vault, reused two ways — `autodetect_vault` = root + `wikis`, `autodetect_inbox` = root + `inbox/<slug>`. The inbox path needs one more piece the others don't: a local, per-machine slug read from `~/.claude/second-brain-inbox/inbox-slug` (written by the shared Second Brain's own onboarding, not by this app) — if that file doesn't exist, auto-detect simply returns `None`, matching the `inbox-review` skill's own "not set up yet" fallback rather than erroring.

**`autodetect_raw` is deliberately *not* built on the shared-root helper — a real bug, caught in live use.** The raw badge triggers `/wiki-builder`, the **personal** skill, which scans a hardcoded personal path (`~/Documents/Claude/Projects/Second Brain/Second Brain Obsidian/raw/`) — not the shared OneDrive vault's own `raw/` folder, even though both are named `raw/` and the shared vault is even symlinked *into* the personal one for browsing (easy to conflate; `wiki-builder`'s own `SKILL.md` explicitly warns about this exact mixup). The first version of this function wrongly reused `autodetect_second_brain_root()` and confidently auto-selected the *shared* team `raw/` folder for every user — caught when Zac noticed the wrong folder had been auto-picked on his own machine. Fixed by pointing `autodetect_raw` at `wiki-builder`'s own scan path directly, independent of the shared-vault probe. Since 0.10.1 it tries, in order: the `SECOND_BRAIN_VAULT_ROOT` override (environment, else `~/.claude/settings.json` `env`, because a Finder-launched app misses `.zshrc`), `~/Documents/Claude/Projects/Second Brain/...`, then the same path inside each OneDrive root (Known Folder Move). `config::onedrive_roots()` lists every `OneDrive*` root; the shared-vault probe also checks `Documents*` containers (Windows SharePoint shortcuts); `autodetect_inbox` falls back to matching the Claude account email (`~/.claude.json`) against `inbox/_roster/*.md` when the slug marker is missing or stale. Not verified on Windows or a KFM machine. That literal path isn't a Zac-specific guess — it's the same path the skill itself expects for anyone who completed the standard Second Brain onboarding, even though Zac's happens to resolve there via a symlink into his personal ZacAI project. The counting logic (`<!-- wiki-processed -->` marker) needed no change — confirmed identical between `wiki-builder` and `sc-wiki-builder`.

**Counting (`counts.rs`):**
- `count_unprocessed_raw` — a raw `.md` file counts as unprocessed if it does **not** contain the literal marker `<!-- wiki-processed -->`, confirmed by reading `sc-wiki-builder`'s own `SKILL.md` rather than assumed. No frontmatter parsing — the marker is the sole authoritative signal per that skill, since raw files arrive from any teammate with inconsistent or missing frontmatter.
- `count_inbox_items` — counts `*.share.md` files, not total file count, confirmed from `inbox-review`'s own skill doc: each item has exactly one companion note (optionally paired with a payload file), so counting notes avoids double-counting pairs.
- Both have a fixture-based unit test (`counts.rs`'s `counts_raw_and_inbox_correctly`).

**Refresh:** same watcher-driven pattern as the vault/tantivy index (§3) — `start_watching_raw`/`start_watching_inbox` debounce filesystem events on each folder and call `recount_raw`/`recount_inbox`, which re-run the count and emit `raw-count-status`/`inbox-count-status` events the frontend listens for. No polling. Verified live: writing a synthetic unprocessed file into the real `raw/` folder moved the badge 1→2 within the debounce window, deleting it moved it back 1→2→1, with no app restart.

**Launch mechanism — `claude://code/new?q=<command>`, no `folder=` param.** This isn't guessed: it's the exact pattern already working in Zac's own `~/Documents/Claude/Projects/ZacAI/tools/dashboard-app-src/` (a separate Swift/WKWebView app). Two things carried over directly from reading that code:
1. `claude://` is the **general Claude Desktop app's** own registered URL scheme (`/Applications/Claude.app`'s `Info.plist` lists `CFBundleURLSchemes: ["claude"]`) — distinct from Claude Code's own `claude-cli://` terminal handler and the VS Code extension's `vscode://anthropic.claude-code` handler, both of which are real and documented but not what was wanted here.
2. **Deliberately no `folder=`/`cwd=` param** — the dashboard's own code comment explains why: a link-supplied folder is always treated as untrusted by Claude Desktop and re-prompts "Trust this workspace?" on every single click. `/wiki-builder` and `/inbox-review` are global skills operating on absolute paths, so no working directory is needed anyway.

Implemented entirely in the frontend (`main.js`'s `launchClaudeCommand`) via `openUrl` from `window.__TAURI__.opener` — no Rust command needed, same as how file-opening already works (§4). Verified live end-to-end: clicking the 📥 badge in the running app opened Claude Desktop with `/wiki-builder` pre-filled, unsent, exactly as documented.

**Settings screen:** the onboarding screen (§5) is no longer single-purpose — it now has four folder sections (Wikis, required; Raw notes, optional; Inbox, optional; Shared vault raw notes, optional, added v3) plus Default-app and Diagnostics groups, each with the same auto-detect-then-confirm-or-browse UX, built from one `makePathSection` factory in `main.js` rather than copy-pasted by hand. As of v5 (§14) this is a full-page grouped-row layout (`.settings-list`/`.setting-row`) matching the Skills/Map views, not the original four narrow centered cards — a header Back button (visible once the vault is configured) replaced the old standalone "Done" button, and both are reached via the same ⚙ button (now `#settings-badge`).

**Not yet verified on Windows** — same category of gap as the rest of this doc's Windows caveats. `claude://` almost certainly works identically (Claude Desktop ships for both platforms and URL-scheme registration is standard cross-platform practice for Electron-style apps), but hasn't been tested on an actual Windows machine.

## 7. Logging & crash capture

`tracing` writes to a daily-rotating file under `app_log_dir()/logs/second-brain-search.log.<date>` (confirmed real location on macOS: `~/Library/Logs/com.zackwolf.second-brain-search/logs/`). Files older than 7 days are pruned on each startup. A `std::panic::set_hook` logs any panic (message + location) to the same file before the process dies, so crashes aren't silently lost.

There is no automatic upload/telemetry — deliberately out of scope. The "Export Logs" button, now in Settings' Diagnostics group (moved off the search-view topbar in v5, §14), calls `revealItemInDir` to open the log folder in Finder/Explorer; a collaborator experiencing an issue attaches the relevant log file manually (Slack/email) for Zac to read. This is a manual, user-initiated export, not a phone-home pipeline.

**Devtools enabled deliberately, including in release builds** (`tauri = { features = ["devtools"] }` in `Cargo.toml`) — right-click → Inspect Element works even in the shipped `.app`/`.exe`. For a small internal tool, being able to ask a collaborator to open the console and paste what they see is worth more than whatever minor security/polish cost comes from devtools being reachable.

## 8. v2 — local chat ("AI Search") — implemented, then removed in v3

Removed in v3: the 0.5B on-device model could not answer reliably (weak retrieval on identifier-heavy pages, degenerate output). Effort went into keyword ranking instead (§4). Gone: `llm.rs`, the chat commands and UI, the `candle`/`tokenizers`/`reqwest`/`rayon`/`sysinfo` dependencies and the ~440 MB model download. Full rationale and the engineering lessons from that era: `CHANGELOG.md`, "Archive: v2 AI Search".

## 9. Packaging & distribution

**Both Mac and Windows now build via GitHub Actions, from a single workflow.** Tauri's Windows target can't be cross-compiled from macOS anyway (needs the MSVC linker, WebView2, NSIS/WiX bundling), so both platforms build on their native GitHub-hosted runners rather than locally. Repo: `https://github.com/zwolf25/second-brain-hub` (private). Workflow: `.github/workflows/build.yml`, triggers on push to `main` or manually (`workflow_dispatch`):
- **v3 rewrite, via `tauri-apps/tauri-action`** (replacing the earlier manual build → upload-artifact → download-artifact → `softprops/action-gh-release` two-job flow): a matrix (two Mac targets, Windows), one job each, each running `tauri-action` directly — it builds, signs (via the updater keypair below), generates the updater's `latest.json` manifest, and publishes straight to a GitHub Release in one step. Uploads go through the GitHub Release-assets API directly, **not** `actions/upload-artifact`'s blob storage (`productionresultssa8.blob.core.windows.net`, the Zscaler-blocked Azure endpoint that forced the old two-job split) — so the old workaround's reason for existing is gone, and the action's documented multi-platform-same-release pattern handles both jobs safely publishing to one tag without the manual job-sequencing the old workflow needed.
- **Real semver tags now** (`v__VERSION__`, substituted from `tauri.conf.json`'s `version` field), not the old `build-N` run-number scheme — required because the updater compares versions to decide whether to prompt, which a monotonic-but-meaningless run number can't support.
- **Mac builds are unsigned** (Apple-notarization-wise; they *are* now Tauri-updater-signed, see below) — full notarization/Apple Developer Program enrollment is still explicitly skipped as unnecessary cost for a handful-of-teammates internal tool. First launch requires a Gatekeeper right-click → Open (or `xattr -cr` the `.app`); see the note below on why *later* updates likely won't hit this again.
- **Intel Macs:** `macos-latest` is arm64, so the matrix builds two Mac targets (`aarch64-apple-darwin`, `x86_64-apple-darwin`; `latest.json` lists both) plus Windows. The Intel entry was added without a known Intel user and has not yet run in CI.
- **Cost caveat:** macOS Actions runners bill at a 10x minute-multiplier vs. Linux/Windows on GitHub's private-repo free tier — a few extra minutes of wall-clock build time costs meaningfully more of the monthly free-minutes budget than before. Worth watching if pushes become frequent.

## 9a. Auto-updater (v3, implemented)

**What changed:** `tauri-plugin-updater` + `tauri-plugin-process` (Rust) and their JS counterparts are now wired in. On launch, `main.js`'s `checkForAppUpdate()` calls the updater's `check()` (exposed on `window.__TAURI__.updater` via `withGlobalTauri`, same pattern as the existing `dialog`/`opener` globals — no bundler needed). If an update's available, a banner appears at the top of the main search page ("⬇ A new version of Second Brain Hub is available" — moved off the topbar in v5, §14, same `.update-banner` styling the Skills-page plugin banner uses); clicking its button calls `downloadAndInstall()` then `relaunch()` (from `window.__TAURI__.process`). No auto-nagging dialog — informational banner, user-initiated install.

**Signing:** updates must be signed or the plugin refuses to install them. A dedicated Ed25519 (minisign-format) keypair was generated via `tauri signer generate` — separate from Apple code-signing/notarization, no cost, no account. The public key lives in `tauri.conf.json`'s `plugins.updater.pubkey`; the private key and its password are GitHub Actions repo secrets (`TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`), consumed by `tauri-action` automatically — never committed to the repo, never in build logs. `bundle.createUpdaterArtifacts: true` in `tauri.conf.json` is what makes the build actually produce the signed updater-compatible archives/`.sig` files `tauri-action` needs.

**Endpoint:** `plugins.updater.endpoints` in `tauri.conf.json` points at `https://github.com/zwolf25/second-brain-hub/releases/latest/download/latest.json` — GitHub always resolves that path to the newest published release's `latest.json` asset, so no separate hosting/CDN is needed; the same Release that already hosts the installers hosts the update manifest.

**Migration caveat, not a bug:** every collaborator's existing install (pre-v3, no updater code in it at all) has no way to detect this release on its own — it's what introduces the updater. One more manual reinstall is required industry-wide, once, to get everyone onto an updater-capable build; every release after that should update in-app. See the README's "Getting updates" section for the collaborator-facing version of this.

**Likely (not yet confirmed live) side benefit for the Gatekeeper warning:** the in-app updater downloads and replaces the `.app` bundle itself rather than going through a browser download, and macOS's quarantine attribute (`com.apple.quarantine`) is typically applied by the *downloading application* (Safari/Chrome), not by arbitrary file writes. If that holds for Tauri's updater downloader too, collaborators may stop seeing the "damaged file"/Gatekeeper block on updates after this one — only the migration reinstall above would still need it. Flagged as a real mechanism, not a guarantee, until verified on an actual update cycle.

**v6 (0.6.0) — source editing (verified live on Mac 2026-10-01: edit/save, Cmd+S, discard dialogs, any local .md; reindex, read-only error and Windows untested):** an Edit button in the viewer swaps the rendered pane for a plain `<textarea>` of the raw markdown body; Save button or Cmd/Ctrl+S writes it back, Cancel discards (confirm if dirty). Explicit save only — no autosave/undo (v0.3.0 decision). Rust (`render.rs`): `read_for_edit` splits the verbatim frontmatter block (`header`, hidden from the editor, written back untouched) from the raw `body` (wikilinks intact, unlike `render_file`); `write_for_edit` writes `~$hub-<name>` then renames (atomic; the `~$` prefix makes the indexer skip the tmp file). `lib.rs`: `can_edit_markdown` (file is writable) decides whether the Edit button shows; any local `.md` is editable, not just the vault (user decision) — the OS default-handler role means files outside the vault can open here too. Collaborators' saves into view-only `wikis/` fail with an OS permission error and the buffer stays open. No new Tauri capability needed (custom commands, not `fs` plugin). **Why this replaced the 2026-08-22 attempt:** that used vendored Toast UI WYSIWYG and showed a blank pane that couldn't be debugged in the installed WKWebView; a textarea has no library/asset surface to fail. Debug future UI work with `npm run tauri dev` (devtools), not the installed bundle.

**Explicitly still out of scope:** telemetry, multi-user sync/accounts/backend, a real vector DB (brute-force cosine is enough at this corpus size), a wikilink graph beyond the Neural Map (§14).

## 10. Capabilities / permissions (`src-tauri/capabilities/default.json`)

Tauri's ACL is deny-by-default per-command **and** per-scope — granting a command permission (e.g. `opener:allow-open-path`) is not sufficient if that permission also requires a path scope and none is configured (see §11 for the bug this caused). Current grants: `core:default`, `opener:default` (URL opening + reveal-in-Finder), `opener:allow-open-path` scoped to `$HOME/**` (covers the OneDrive vault at any username; broad but low-risk since it only permits "open with OS default handler," not raw file read/write), `opener:allow-open-url` scoped to `claude://*` (powers the Raw/Inbox badge launch, §6 — `opener:default`'s bundled URL scope only covers `mailto:`/`tel:`/`http:`/`https:`, not custom schemes), `dialog:default` (folder picker), `updater:default` (check/download/install, §9a), `process:allow-restart` (relaunch after an update installs, §9a — narrower than `process:default`, which would also grant `exit`).

## 11. Real bugs found and fixed during live testing

Two bugs still instructive for the current code (the v2-era ones moved to `CHANGELOG.md`, "Archive: v2 AI Search").

1. **Silent permission failure on file-open:** `opener:allow-open-path` was granted but with no `scope` — Tauri's ACL denies-by-default even with the permission listed, so every open attempt failed with "Not allowed to open path X," silently, because the JS click handler had no `.catch()`. **Fixed both ends:** added `"allow": [{ "path": "$HOME/**" }]` to the capability, and added error surfacing (`alert(...)` on rejection) so any future permission/IO failure is visible instead of silent.
2. **Raw-folder auto-detect confidently found the wrong folder** (§6) — built on the same shared-OneDrive-root helper used for the vault and inbox, so it always found the *shared team* `raw/` folder, even though the raw badge is meant to trigger `/wiki-builder`, the *personal* skill scanning a completely different path. Caught live: Zac noticed the auto-selected folder didn't match his actual personal raw notes. The two paths are genuinely easy to conflate — same folder name, and the shared vault is even symlinked into the personal one for browsing — which is exactly why `wiki-builder`'s own `SKILL.md` calls out the mixup explicitly. **Fixed:** `autodetect_raw` now checks `wiki-builder`'s own hardcoded scan path directly, with no dependency on the OneDrive/shared-root probe at all. General lesson: two features that both auto-detect "a `raw/` folder" aren't necessarily looking for the same folder — check what the *downstream skill* actually scans, not just what the feature is named.

## 13. v4 — in-app markdown viewer + default `.md` handler

**What it is:** double-clicking a search result now renders the file in-app (`render.rs`, `pulldown-cmark`) in a clean, full-width, Typora-like reading pane (content fills the window and grows/shrinks with it; the original 720px centered column cap was removed) — no raw-markdown/gutter chrome in reading mode (editing: v6 below) — instead of shelling out to the OS default app. An "Open externally" button in the viewer covers the edit case, and a "✦ Ask Claude" button (0.13.0) opens a Claude Desktop session via `launchClaudeCommand` with `Read <path> and answer my question about it: ` pre-filled (hidden while editing). Raw HTML in markdown is shown as text (`render::sanitize_event`); only the app's own wikilink anchors render. The app can also be registered as the OS's `.md`/`.markdown` handler, so a double-click anywhere on the machine opens it, guided from a new Settings section.

**Rendering:** `frontmatter::parse` gives the title; the body comes from `split_frontmatter` (`pub(crate)`). `render::link_wikilinks` turns `[[target|alias]]` into `<a class="wikilink" data-target=…>` before markdown parsing, skipping fenced code and inline code. **Navigation (0.11.0):** the page resolves a click with `resolve_wikilink` (exact stem, then case-insensitive, flat vault layout like the indexer) and opens it with `openInViewer(…, {keepHistory:true})`; `viewerHistory` makes Back walk the pages visited. A hub's `## Child wikis` list is ordinary wikilinks, so it navigates too. **Backlinks:** `get_backlinks` (only for files inside the vault) scans the vault's wikilinks via `graph::backlinks` and the page appends a "Linked from (N)" row to the content. GFM extras (tables, footnotes, strikethrough, tasklists) via `pulldown_cmark::Options`. Local image `src` rewriting happens in `main.js` (not Rust) via `convertFileSrc`, resolved against the source file's directory — keeps `render.rs` a pure, plain-string-testable function.

**OS launch handling:** `tauri-plugin-single-instance` (registered first, per its own requirement) plus `RunEvent::Opened` (macOS open-file Apple Events) plus `std::env::args()` (Windows/Linux cold start) all funnel into one `handle_open_file`. **Real bug found and fixed via live testing:** the first version stored the launched path in Tauri-managed `AppState` — but macOS can deliver the open-file Apple Event *before* `.setup()` runs `app.manage(state)`, so `app.state::<Arc<AppState>>()` panicked, and since that call crosses tao's ObjC delegate callback (no unwind allowed there), the panic was a hard process abort, not a catchable error — reliably crashed on every cold "Open With" launch. **Fixed** by moving the pending-path storage to a plain module-level `static PENDING_OPEN_PATH: Mutex<Option<String>>` (`lib.rs`), which needs no `.manage()` call first. Verified live afterward: cold launch with a file, and a second file opened while already running (routes into the existing window, no duplicate process) both work cleanly.

**Default-handler registration (`default_handler.rs`, macOS-only):** raw `extern "C"` calls to `LSSetDefaultRoleHandlerForContentType`/`LSCopyDefaultRoleHandlerForContentType` (via `core-foundation`), not a full ObjC-bridge crate — deliberately, for two functions. Declared cross-platform via `tauri.conf.json`'s `bundle.fileAssociations` (`ext`, `role: "Viewer"`, `rank: "Alternate"`, `contentTypes: ["net.daringfireball.markdown"]`) — this one config block generates the macOS `Info.plist` `CFBundleDocumentTypes`/`LSHandlerRank` entries **and** the Windows NSIS/registry association; no separate hand-written `Info.plist` fragment needed, simpler than originally planned.

**Two real findings from live-testing this on the actual dev machine (macOS 26.5.2), not yet confirmed across other macOS versions:**
1. **`rank` matters, don't default it.** The first build omitted `rank` (schema default: `"Editor"`... resolved by the bundler to `LSHandlerRank: "Default"` here), which meant just *building and launching the debug bundle during testing* silently made this app the machine's real default `.md` handler — before any "Set as Default" button existed or was clicked. Fixed by setting `rank: "Alternate"`, confirmed via the built `Info.plist` — registering as an option no longer auto-claims default status; only the explicit user-initiated `set_default_md_handler` call does that.
2. **`LSSetDefaultRoleHandlerForContentType`'s write half looks unreliable on current macOS, independent of the `rank` fix above.** After correcting `rank`, explicitly calling the setter (to restore a different app as default) reported success (`OSStatus 0`) but `LSCopyDefaultRoleHandlerForContentType` kept reading back this app as default — ground-truth confirmed via `open` actually launching this app, not the one just set. Finder's own Get Info → "Open with" panel, checked afterward, *did* show the other app correctly, suggesting the legacy read API (or some layer of it) is stale/inconsistent on this OS version rather than the write being truly ineffective — unresolved which side is actually wrong. **Not treated as a blocker**: the Settings UI (`main.js`) re-checks `is_default_md_handler` after every "Set as Default" click and shows the honest resulting status rather than assuming success, and the manual Finder-based fallback is always available regardless. Flag for follow-up if a collaborator reports the button not sticking.

**Windows:** no programmatic default-setting exists (Microsoft has blocked this since Windows 8) — the Settings section instead shows a static instructional message plus a button that opens `ms-settings:defaultapps` (new `ms-settings:*` entry in `opener:allow-open-url`'s capability scope, same `openUrl` mechanism already used for `claude://` links, §6). No live "currently default" status readback on Windows — none exists to query, shown honestly rather than faked.

**ACL additions:** `app.security.assetProtocol` (`enable: true`, `scope: ["$HOME/**"]`) plus the `protocol-asset` Cargo feature on `tauri`, both required for `convertFileSrc` to serve local vault images to the viewer — live-verified working for `$HOME`-scoped paths and correctly 403-blocking paths outside that scope (e.g. `/private/tmp`), confirmed via the browser console rather than assumed.

**What it is:** a searchable catalog of every skill in the shared vault's `skills-repo` (`skills.rs`, new `get_skills` command), opened from an always-visible topbar badge, plus a redesign that brings Settings into the same full-page header-+-scrolling-list pattern the Map view already used, so Skills/Map/Settings now share one visual language instead of Settings being a one-off centered card.

**Drift re-check on Refresh:** the drift check (`check_plugin_drift`, `lib.rs`) runs at launch, on shared-raw path change, and now on every manual Refresh. `#reindex-btn`'s handler calls the new `refresh_plugin_drift` command (re-runs the check, updates the cached `plugin_drift`, returns it) and pipes the result into `renderSkillsBadge`, so the topbar icon (`✨` → `🧩`) and the Skills-page banner clear together right after the user updates plugins — no app restart. Previously only `get_plugin_drift` (cache read) existed and Refresh touched just the search index.

**Custom tooltip:** the native `title` attribute's hover delay was too slow for a quick glance, and it's suppressed outright in some embedded webviews (confirmed live). **`skills.rs`:** walks `<shared_vault_root>/skills-repo/*/skills/*/SKILL.md`, reusing `frontmatter::split_frontmatter` rather than re-parsing YAML. `added` is the file's mtime formatted `YYYY-MM-DD` (hand-rolled civil-from-days conversion — no date/time crate was a dependency yet, not worth adding for one format call). **Real bug found in the unit test, not in production:** the first cut sorted by the *formatted date string*, which ties for any two skills added the same calendar day and silently falls back to filesystem read order — caught because the test wrote two fixture skills 1.1s apart and asserted descending order, which failed. Fixed by sorting on the raw `SystemTime` internally and only formatting to a date string for display. General lesson: a display-granularity value (day) is the wrong sort key once inputs can tie at that granularity — sort on the full-precision source value, format separately.

**Search:** client-side subsequence fuzzy match (`fuzzyScore` in `main.js`) over `name + plugin + description` for all skills fetched fresh on each view-open (`get_skills` does a full ~150-file walk every call rather than caching — cheap enough that staleness risk wasn't worth the cache invalidation complexity). **Refresh loading overlay:** `#reindex-btn` now shows a full-window spinner overlay while a *manual* refresh runs, gated by a module-level `awaitingManualRefresh` flag checked inside the existing `renderStatus()` `index-status` handler — not a fixed timer, and deliberately not wired to every `index-status` event, so the sub-300ms background reindexes a file-watcher event triggers on its own don't flash the overlay.

**App-update banner moved off the topbar:** the old `#update-badge` topbar button is gone; an available *app* update (distinct from a *skill-plugin* update, above) now shows as a banner at the top of the main search page, reusing the same `.update-banner` styling as the Skills-page plugin banner. Same underlying `pendingUpdate`/`checkForAppUpdate()`/`downloadAndInstall()`/`relaunch()` logic as before (§9a) — purely a presentation move.

The mockup's own theory here (text-presentation selector, matching how a browser renders the bare codepoint) was tried first and was wrong — live-tested against the real topbar, it made the gear render smaller and monochrome while every other topbar icon (🧠, 🧩, 📄, 📥, 🌐) is full-size color emoji, which looked *more* inconsistent, not less. Result is stored on the entry (`header`, `header_checked`) and rendered as `type: transcript-ai` with `## AI Summary` / `## Key Actions` / `## Owner Mentions` above the cues. Hashing, near-dup shingles and categorization read cues only, so the header never changes dedupe or category. Entries from before this (or with an old-style title) re-scan once; only headered files are rewritten. Mirrored in the `vtt-normalizer` skill (`normalize_vtt.py`).
- **Filenames:** `Title_YYYY-MM-DD_Transcript.vtt` and the newer `Title_YYYY-MM-DD_HH-MM_Transcript.vtt` both parse to a clean title and date (a dateless row sorts last).
- **Summary row:** rows with a header show a chevron after the checkbox; it expands a panel (summary, key actions, mentions of the owner). Expansion state is `expandedTranscripts` in `main.js` and survives re-renders; →/← toggles on a focused row. Audit events never carry header text.
