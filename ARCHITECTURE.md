# Architecture — Second Brain Hub

Local desktop app that indexes the shared SC PM "Second Brain" wiki vault (OneDrive) and gives fast fuzzy full-text search over it, plus local semantic "chat" search. Runs entirely on the collaborator's machine — no server, no cloud calls, no API tokens. Written for a small internal team, not a public product; scope decisions below favor simplicity over generality.

(Product name is "Second Brain Hub"; the underlying project folder, npm package, and Rust crate/binary are still named `second-brain-search` — internal plumbing, not user-visible, left as-is rather than doing a full rename.)

Status: **v1 (search) and the Raw/Inbox heads-up badges are implemented and verified against the real shared vault**, including live GUI testing that surfaced and fixed several real bugs (§11). Windows builds now ship via GitHub Actions CI (§9) — the earlier "no Windows machine" blocker is resolved. **v2 (local chat / "AI Search") was implemented, then removed in v3** — see §8 for why. **v3 also added:** smarter keyword-search ranking (§4), a third "shared vault freshness" badge (§6), and an in-app auto-updater (§9a) — the last of these is implemented but not yet verified against a real release cycle (§12).

## 1. Stack

- **Tauri 2** (Rust backend + OS-native webview). Chosen over Electron for installer size (~10-20MB vs ~150-200MB) and idle resource footprint — this machine had no Rust toolchain when the project started, installed via `rustup`.
- **tantivy** — embedded Lucene/BM25-style full-text engine, runs in-process, no server. Gives genuine fuzzy (edit-distance) search, which tantivy's default `QueryParser` does not do on its own — the query layer builds `FuzzyTermQuery` clauses manually, alongside exact-term and phrase clauses (see §4).
- **Plain HTML/CSS/JS frontend**, no framework. The UI is a search box, a results list, topbar heads-up badges, and a settings/onboarding screen — a framework buys nothing at this scope.
- `tracing` + `tracing-appender` for structured local logging; `notify` + `notify-debouncer-mini` for vault/raw/inbox file-watching; `walkdir` for directory traversal; `serde_yaml` for frontmatter parsing; `anyhow` for error plumbing.
- (v2 also used `candle`, a pure-Rust ML framework, for on-device chat/"AI Search" — removed in v3, see §8. No longer a dependency.)

## 2. Module layout (`src-tauri/src/`)

| File | Responsibility |
|---|---|
| `config.rs` | `AppConfig` (`vault_path`, `raw_path`, `inbox_path`), load/save as plain JSON in `app_config_dir()`, path validation, OneDrive path auto-detection (shared `autodetect_second_brain_root` helper, reused for all three paths) |
| `frontmatter.rs` | Splits `---`-delimited YAML frontmatter from markdown body (hand-rolled, not a crate — simple enough and avoids depending on an unfamiliar crate's exact API), extracts title (first `# ` heading, fallback filename), strips `[[wikilink]]` brackets for clean display |
| `index.rs` | tantivy schema definition, full vault walk + rebuild, index open. Includes a fuzzy-search round-trip test |
| `search.rs` | Query construction (title/topics/body — exact-term, fuzzy, and phrase clauses, stopword-filtered; title and topics boosted highest), snippet generation, `SearchResult` shape returned to the frontend. Includes ranking-quality tests |
| `counts.rs` | `count_unprocessed_raw` (missing `<!-- wiki-processed -->` marker) and `count_inbox_items` (`*.share.md` count) for the topbar heads-up badges. Includes a fixture-based unit test |
| `watcher.rs` | Debounced (400ms) filesystem watch, triggers a full reindex (vault) or recount (raw/inbox) on any change — generic over which folder it's watching |
| `logging.rs` | Rolling daily log file, 7-day retention pruning, panic hook that logs crashes to the same file |
| `lib.rs` | Tauri app wiring: `AppState`, command registration, startup sequence |

## 3. Indexing pipeline

On startup (if a vault is configured) and on every debounced file-watcher event, `index::rebuild()` does a **full re-walk-and-reindex** — deletes the on-disk tantivy index directory and rebuilds it from scratch by walking every `.md` file in the vault root. This is simpler than incremental per-file diffing and, at real-world scale (73 files, ~1.8MB), completes in well under a second — confirmed by the log timestamps during verification (sub-300ms `Preparing commit` → `Garbage collect` cycles). Revisit only if a much larger vault makes this measurably slow.

**tantivy schema:** `path` (STRING, STORED — canonical doc id, also the click-through target), `title` (TEXT, STORED), `body` (TEXT, STORED, wikilink brackets stripped), `topics` (TEXT, STORED, from frontmatter, wikilink brackets stripped), `updated` (STRING, STORED, from frontmatter).

**Frontmatter handling:** every wiki file's frontmatter has `type`, `topics` (a list), `created`, `updated` — no `title` field, confirmed by reading real files, hence the first-`# `-heading fallback. OneDrive transient files (filenames starting `~$`) are skipped; unreadable files are skipped rather than aborting the whole rebuild.

**Scope note:** this app indexes the **shared vault only**. Zac's separate personal ZacAI vault and its `second-brain/` pointer-stub subfolder are explicitly out of scope — dropped early to keep indexing/onboarding simple (no stub-dedup logic, no vault-source filter UI). If chat is enabled, `llm::build_chunk_embeddings` re-walks the same vault independently (see §8) — two walks of the same small tree, not shared code, judged not worth a shared-walker abstraction at this scale.

## 4. Search (Search tab)

Query flow: debounced (~200ms) keystroke in the frontend → `search_vault` Tauri command → `search::search()`:
1. Tokenize the query on whitespace, lowercase each token.
2. Filter out stopwords (a small hardcoded list — "how"/"do"/"i"/"the"/etc.) *for clause-building purposes only* — the tantivy fields themselves still index stopwords normally, so exact/phrase matching against them still works. Falls back to the unfiltered token list if the whole query happens to be nothing but stopwords, so a degenerate query still searches on something. This matters more post-v2 (§8): with AI Search gone, people type the same natural-language questions ("how do I enable rate validation") into keyword search that they used to type into the AI box, and unfiltered fuzzy matching on "how"/"do"/"i" was diluting ranking exactly for that query shape.
3. For each remaining (significant) token, build **two** `Should` clauses per field (`title` boosted 3.0×/2.0×, `topics` 2.0×/1.5×, `body` 1.5×/unboosted) — an exact non-fuzzy `TermQuery` at the higher boost, and a `FuzzyTermQuery` (edit distance 1 for short tokens ≤5 chars, 2 for longer ones) at the lower boost. Two clauses per field, not one, because the old fuzzy-only version scored a precise match and a same-distance typo match identically — nothing ranked a real hit above a near-miss.
4. If the query has 2+ tokens, add one more heavily-boosted (5.0×) `PhraseQuery` clause against `body` for the literal token sequence — a page containing the exact multi-word phrase (a distinctive feature name, say) jumps above pages that only match scattered individual terms.
5. All clauses OR'd together (`Occur::Should`) in a `BooleanQuery`, `TopDocs::with_limit(30)`.
6. Generate highlighted snippets via tantivy's `SnippetGenerator` on the `body` field; falls back to a plain 220-char excerpt if snippet generation yields nothing.

Tested in `search.rs` itself: `exact_match_outranks_fuzzy_typo_match` and `stopword_heavy_natural_language_query_still_surfaces_the_right_doc`. `index.rs`'s original `rebuild_and_fuzzy_search_round_trip` still covers the index-rebuild path and basic typo tolerance.

**Opening a result:** double-click (not single-click — deliberate, so scrolling/scanning results doesn't accidentally open files; a "Double-click a result to open the file" hint is shown under the search box). Calls `tauri-plugin-opener`'s `openPath` directly from the frontend (`window.__TAURI__.opener` global). See §11 for a real permission bug this hit and how it was fixed.

## 5. Onboarding & config

First run: no `config.json` in `app_config_dir()` (or no `vault_path` in it) → onboarding screen. `autodetect_vault` command probes for a OneDrive folder under `~/Library/CloudStorage` (macOS) or the user's home directory (Windows-style layout) containing `SVC-Product_Management - Second Brain/wikis` with at least one `.md` file. If found, the user gets a one-click "Use detected folder" button; otherwise a native folder-picker (`tauri-plugin-dialog`) is the fallback — every collaborator's OneDrive path differs by username/OS, so this can never be hardcoded.

Config persists as plain `serde_json`-written JSON — no config-management plugin, three fields doesn't warrant one. As of §6 below, `AppConfig` actually has three path fields (`vault_path`, `raw_path`, `inbox_path`), so "three fields doesn't warrant a plugin" now describes the real shape, not just the vault.

## 6. Raw & Inbox heads-up badges + new-session button (topbar, omnipresent)

Four always-visible controls in the topbar (not inside the search panel, so they're always on-screen): a 📄 badge for unprocessed raw notes (`wiki-builder`'s job), a 📥 badge for pending inbox items (`inbox-review`'s job), a 🌐 badge for the total unprocessed raw-file count across the *whole shared* Second Brain vault (added in v3 — see below), and a Claude-icon button that opens a blank new Claude Desktop session (`claude://code/new`, no `q` param — nothing pre-filled, unlike the badges below). The Claude icon itself is copied from the locally-installed `/Applications/Claude.app` bundle (`ion-dist/images/claude_app_icon.png`) rather than recreated, so it matches the real app icon exactly.

Clicking the 📄/📥 badges jumps straight into Claude Desktop with the matching slash command pre-filled. The 🌐 shared-raw badge is different on purpose: it's **purely informational**, a "freshness" signal for the wikis a collaborator is reading, not an action they can take (they didn't submit those files, someone else on the team did). Clicking it just reveals the shared `raw/` folder in Finder/Explorer (`revealItemInDir`) instead of launching a Claude command.

**Shared-raw badge, v3 addition:** reuses the same counting logic (`counts::count_unprocessed_raw` — folder-agnostic, marker-based) and the same 4-slot settings pattern as the other three paths, just pointed at a different folder: `config::autodetect_shared_raw()` is `autodetect_second_brain_root()?.join("raw")` (the shared vault's own `raw/`, not `wiki-builder`'s personal path used by `autodetect_raw`). No new counting logic was needed — the existing marker-based function already works against any raw folder, including this one. **Deliberately not per-user-attributed:** the raw files carry no author/submitter frontmatter field today, so "unprocessed files *you* added" isn't buildable without also changing the note-writing skills outside this repo — shipped as a total-across-everyone count instead, which is still a genuine freshness signal without that dependency.

**Paths & auto-detect:** `config::autodetect_second_brain_root()` is the OneDrive-probing logic originally written just for the vault, reused two ways — `autodetect_vault` = root + `wikis`, `autodetect_inbox` = root + `inbox/<slug>`. The inbox path needs one more piece the others don't: a local, per-machine slug read from `~/.claude/second-brain-inbox/inbox-slug` (written by the shared Second Brain's own onboarding, not by this app) — if that file doesn't exist, auto-detect simply returns `None`, matching the `inbox-review` skill's own "not set up yet" fallback rather than erroring.

**`autodetect_raw` is deliberately *not* built on the shared-root helper — a real bug, caught in live use.** The raw badge triggers `/wiki-builder`, the **personal** skill, which scans a hardcoded personal path (`~/Documents/Claude/Projects/Second Brain/Second Brain Obsidian/raw/`) — not the shared OneDrive vault's own `raw/` folder, even though both are named `raw/` and the shared vault is even symlinked *into* the personal one for browsing (easy to conflate; `wiki-builder`'s own `SKILL.md` explicitly warns about this exact mixup). The first version of this function wrongly reused `autodetect_second_brain_root()` and confidently auto-selected the *shared* team `raw/` folder for every user — caught when Zac noticed the wrong folder had been auto-picked on his own machine. Fixed by pointing `autodetect_raw` at `wiki-builder`'s own hardcoded scan path directly, independent of the OneDrive probe entirely. That literal path isn't a Zac-specific guess — it's the same path the skill itself expects for anyone who completed the standard Second Brain onboarding, even though Zac's happens to resolve there via a symlink into his personal ZacAI project. The counting logic (`<!-- wiki-processed -->` marker) needed no change — confirmed identical between `wiki-builder` and `sc-wiki-builder`.

**Counting (`counts.rs`):**
- `count_unprocessed_raw` — a raw `.md` file counts as unprocessed if it does **not** contain the literal marker `<!-- wiki-processed -->`, confirmed by reading `sc-wiki-builder`'s own `SKILL.md` rather than assumed. No frontmatter parsing — the marker is the sole authoritative signal per that skill, since raw files arrive from any teammate with inconsistent or missing frontmatter.
- `count_inbox_items` — counts `*.share.md` files, not total file count, confirmed from `inbox-review`'s own skill doc: each item has exactly one companion note (optionally paired with a payload file), so counting notes avoids double-counting pairs.
- Both have a fixture-based unit test (`counts.rs`'s `counts_raw_and_inbox_correctly`).

**Refresh:** same watcher-driven pattern as the vault/tantivy index (§3) — `start_watching_raw`/`start_watching_inbox` debounce filesystem events on each folder and call `recount_raw`/`recount_inbox`, which re-run the count and emit `raw-count-status`/`inbox-count-status` events the frontend listens for. No polling. Verified live: writing a synthetic unprocessed file into the real `raw/` folder moved the badge 1→2 within the debounce window, deleting it moved it back 1→2→1, with no app restart.

**Launch mechanism — `claude://code/new?q=<command>`, no `folder=` param.** This isn't guessed: it's the exact pattern already working in Zac's own `~/Documents/Claude/Projects/ZacAI/tools/dashboard-app-src/` (a separate Swift/WKWebView app). Two things carried over directly from reading that code:
1. `claude://` is the **general Claude Desktop app's** own registered URL scheme (`/Applications/Claude.app`'s `Info.plist` lists `CFBundleURLSchemes: ["claude"]`) — distinct from Claude Code's own `claude-cli://` terminal handler and the VS Code extension's `vscode://anthropic.claude-code` handler, both of which are real and documented but not what was wanted here.
2. **Deliberately no `folder=`/`cwd=` param** — the dashboard's own code comment explains why: a link-supplied folder is always treated as untrusted by Claude Desktop and re-prompts "Trust this workspace?" on every single click. `/wiki-builder` and `/inbox-review` are global skills operating on absolute paths, so no working directory is needed anyway.

Implemented entirely in the frontend (`main.js`'s `launchClaudeCommand`) via `openUrl` from `window.__TAURI__.opener` — no Rust command needed, same as how file-opening already works (§4). Verified live end-to-end: clicking the 📥 badge in the running app opened Claude Desktop with `/wiki-builder` pre-filled, unsent, exactly as documented.

**Settings screen:** the onboarding screen (§5) is no longer single-purpose — it now has four sections (Wikis, required; Raw notes, optional; Inbox, optional; Shared vault raw notes, optional, added v3), each with the same auto-detect-then-confirm-or-browse UX, built from one `makePathSection` factory in `main.js` rather than copy-pasted by hand. Vault still gates the app (a "Done" button only appears once it's set); the other three are purely optional and can be left unset or configured later via the same ⚙ button (now labeled "Settings" instead of "Change vault folder").

**Not yet verified on Windows** — same category of gap as the rest of this doc's Windows caveats. `claude://` almost certainly works identically (Claude Desktop ships for both platforms and URL-scheme registration is standard cross-platform practice for Electron-style apps), but hasn't been tested on an actual Windows machine.

## 7. Logging & crash capture

`tracing` writes to a daily-rotating file under `app_log_dir()/logs/second-brain-search.log.<date>` (confirmed real location on macOS: `~/Library/Logs/com.zackwolf.second-brain-search/logs/`). Files older than 7 days are pruned on each startup. A `std::panic::set_hook` logs any panic (message + location) to the same file before the process dies, so crashes aren't silently lost.

There is no automatic upload/telemetry — deliberately out of scope. The "Logs" button in the search view's topbar calls `revealItemInDir` to open the log folder in Finder/Explorer; a collaborator experiencing an issue attaches the relevant log file manually (Slack/email) for Zac to read. This is a manual, user-initiated export, not a phone-home pipeline.

**Fixed:** `chat_availability` and `enable_chat` now call `tracing::info!` at each stage (called, downloading/loading, done + chunk count) — this gap (originally flagged here as "not yet fixed") turned out to matter in practice: it's what let the mutex-contention bug in §11 get diagnosed instead of staying a mystery.

**Devtools enabled deliberately, including in release builds** (`tauri = { features = ["devtools"] }` in `Cargo.toml`) — right-click → Inspect Element works even in the shipped `.app`/`.exe`. For a small internal tool, being able to ask a collaborator to open the console and paste what they see is worth more than whatever minor security/polish cost comes from devtools being reachable. This is what actually cracked the render-freeze bug in §11 — `tracing` alone wasn't enough since that bug was a *frontend* rendering issue, not a Rust-side one.

## 8. v2 — local chat ("AI Search") — implemented, then removed in v3

**What it was:** a toggle in the topbar that switched from keyword search to a natural-language question box, backed by two on-device models via `candle` — `all-MiniLM-L6-v2` for embedding/retrieval and `Qwen2-0.5B-Instruct` (Q4_0 GGUF) for answer synthesis, fused via Reciprocal Rank Fusion with the existing tantivy keyword index. Fully implemented, shipped, and put through substantial live-testing hardening (§11 #1–2, #4–11 are all from this era).

**Why it was removed:** the answer-synthesis model was too weak for reliable production use. Real, evidenced findings from live testing (kept here as the record of *why*, not as current-state documentation):
- On specific/technical queries, retrieval itself struggled — a documented gap where dense identifier-heavy content (e.g. a feature-flag reference list) embedded too weakly to surface, even after the RRF hybrid-retrieval fix narrowed it (rank ~13, not rank 1).
- Even with retrieval working, the 0.5B generation model periodically produced degenerate output — fabricating a whole new conversation turn as plain text past its real answer, or echoing the question back verbatim instead of answering. Multiple rounds of guardrails shipped (repeat-penalty, stop-token + plain-text-marker truncation, exact-echo detection, single-threaded determinism fix) and each helped, but none addressed the root cause: a model this small has a real capability ceiling on a laptop CPU. Bumping to 1.5B-Instruct was tested and didn't meaningfully help (same retrieval-starved context, just slower).
- Conclusion: continuing to patch symptom-by-symptom wasn't converging on "reliably good," because the ceiling was the model's capability, not a fixable bug. Decision: remove AI Search entirely and redirect the effort into making keyword search itself smarter (exact-match + phrase-match boosting, stopword handling — see §4) — a more modest but much more reliable improvement, and one every query benefits from instead of only the subset of users who'd opt into a flaky AI mode.

**What's gone:** `llm.rs` (deleted), the `chat_availability`/`enable_chat`/`related_docs`/`write_answer` commands, the `embedding_model`/`chunk_embeddings` app state, the AI Search UI toggle and chat panel, and the `candle-core`/`candle-nn`/`candle-transformers`/`tokenizers`/`reqwest`/`rayon`/`sysinfo` dependencies (all were only used by this feature). This also dropped the ~440MB one-time model download and shrank the build.

Full implementation detail (chunking, RRF math, the TLS/Zscaler download fix, the model-size ladder, every live-testing bug and fix) is preserved in this file's git history if it's ever useful again — not worth keeping inline now that the code itself is gone.

## 9. Packaging & distribution

**Both Mac and Windows now build via GitHub Actions, from a single workflow.** Tauri's Windows target can't be cross-compiled from macOS anyway (needs the MSVC linker, WebView2, NSIS/WiX bundling), so both platforms build on their native GitHub-hosted runners rather than locally. Repo: `https://github.com/zwolf25/second-brain-hub` (private). Workflow: `.github/workflows/build.yml`, triggers on push to `main` or manually (`workflow_dispatch`):
- **v3 rewrite, via `tauri-apps/tauri-action`** (replacing the earlier manual build → upload-artifact → download-artifact → `softprops/action-gh-release` two-job flow): a `[macos-latest, windows-latest]` matrix, one job per platform, each running `tauri-action` directly — it builds, signs (via the updater keypair below), generates the updater's `latest.json` manifest, and publishes straight to a GitHub Release in one step. Uploads go through the GitHub Release-assets API directly, **not** `actions/upload-artifact`'s blob storage (`productionresultssa8.blob.core.windows.net`, the Zscaler-blocked Azure endpoint that forced the old two-job split) — so the old workaround's reason for existing is gone, and the action's documented multi-platform-same-release pattern handles both jobs safely publishing to one tag without the manual job-sequencing the old workflow needed.
- **Real semver tags now** (`v__VERSION__`, substituted from `tauri.conf.json`'s `version` field), not the old `build-N` run-number scheme — required because the updater compares versions to decide whether to prompt, which a monotonic-but-meaningless run number can't support.
- **Mac builds are unsigned** (Apple-notarization-wise; they *are* now Tauri-updater-signed, see below) — full notarization/Apple Developer Program enrollment is still explicitly skipped as unnecessary cost for a handful-of-teammates internal tool. First launch requires a Gatekeeper right-click → Open (or `xattr -cr` the `.app`); see the note below on why *later* updates likely won't hit this again.
- **Caveat, not yet resolved:** GitHub's `macos-latest` runner is Apple Silicon (arm64), so the produced `.dmg` is arm64-only — an Intel Mac collaborator would need a universal/x86_64 build, which this workflow doesn't produce yet. Flag if anyone on an Intel Mac needs this.
- **Cost caveat:** macOS Actions runners bill at a 10x minute-multiplier vs. Linux/Windows on GitHub's private-repo free tier — a few extra minutes of wall-clock build time costs meaningfully more of the monthly free-minutes budget than before. Worth watching if pushes become frequent.

## 9a. Auto-updater (v3, implemented)

**What changed:** `tauri-plugin-updater` + `tauri-plugin-process` (Rust) and their JS counterparts are now wired in. On launch, `main.js`'s `checkForAppUpdate()` calls the updater's `check()` (exposed on `window.__TAURI__.updater` via `withGlobalTauri`, same pattern as the existing `dialog`/`opener` globals — no bundler needed). If an update's available, a small topbar button ("⬇ Update available") appears; clicking it calls `downloadAndInstall()` then `relaunch()` (from `window.__TAURI__.process`). No auto-nagging dialog — informational badge, user-initiated install, matching the rest of this app's topbar-badge conventions (§6).

**Signing:** updates must be signed or the plugin refuses to install them. A dedicated Ed25519 (minisign-format) keypair was generated via `tauri signer generate` — separate from Apple code-signing/notarization, no cost, no account. The public key lives in `tauri.conf.json`'s `plugins.updater.pubkey`; the private key and its password are GitHub Actions repo secrets (`TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`), consumed by `tauri-action` automatically — never committed to the repo, never in build logs. `bundle.createUpdaterArtifacts: true` in `tauri.conf.json` is what makes the build actually produce the signed updater-compatible archives/`.sig` files `tauri-action` needs.

**Endpoint:** `plugins.updater.endpoints` in `tauri.conf.json` points at `https://github.com/zwolf25/second-brain-hub/releases/latest/download/latest.json` — GitHub always resolves that path to the newest published release's `latest.json` asset, so no separate hosting/CDN is needed; the same Release that already hosts the installers hosts the update manifest.

**Migration caveat, not a bug:** every collaborator's existing install (pre-v3, no updater code in it at all) has no way to detect this release on its own — it's what introduces the updater. One more manual reinstall is required industry-wide, once, to get everyone onto an updater-capable build; every release after that should update in-app. See the README's "Getting updates" section for the collaborator-facing version of this.

**Likely (not yet confirmed live) side benefit for the Gatekeeper warning:** the in-app updater downloads and replaces the `.app` bundle itself rather than going through a browser download, and macOS's quarantine attribute (`com.apple.quarantine`) is typically applied by the *downloading application* (Safari/Chrome), not by arbitrary file writes. If that holds for Tauri's updater downloader too, collaborators may stop seeing the "damaged file"/Gatekeeper block on updates after this one — only the migration reinstall above would still need it. Flagged as a real mechanism, not a guarantee, until verified on an actual update cycle.

**Explicitly still out of scope:** telemetry, multi-user sync/accounts/backend, a real vector DB (brute-force cosine is enough at this corpus size), a wikilink cross-reference graph UI (brackets are just stripped for display).

## 10. Capabilities / permissions (`src-tauri/capabilities/default.json`)

Tauri's ACL is deny-by-default per-command **and** per-scope — granting a command permission (e.g. `opener:allow-open-path`) is not sufficient if that permission also requires a path scope and none is configured (see §11 for the bug this caused). Current grants: `core:default`, `opener:default` (URL opening + reveal-in-Finder), `opener:allow-open-path` scoped to `$HOME/**` (covers the OneDrive vault at any username; broad but low-risk since it only permits "open with OS default handler," not raw file read/write), `opener:allow-open-url` scoped to `claude://*` (powers the Raw/Inbox badge launch, §6 — `opener:default`'s bundled URL scope only covers `mailto:`/`tel:`/`http:`/`https:`, not custom schemes), `dialog:default` (folder picker), `updater:default` (check/download/install, §9a), `process:allow-restart` (relaunch after an update installs, §9a — narrower than `process:default`, which would also grant `exit`).

## 11. Real bugs found and fixed during live testing

Live GUI testing (not just automated tests) surfaced several real issues automated tests didn't catch — worth recording since they're the kind of thing that'll recur if this pattern (Tauri + candle + reqwest) gets reused elsewhere. **Most of these (#1, #2, #4–#11) are from the v2 "AI Search" era, removed in v3 (§8) — kept as historical engineering-lesson record, not as current-state documentation; the general lessons in each (mutex-across-computation, render-thread starvation, cross-platform systems-info gotchas) outlive the specific feature.**

1. **Download hang risk:** `reqwest::blocking::get` (the free function) has no timeout. A real network failure would hang the download — and the UI waiting on it — forever with no error. **Fixed:** build an explicit `reqwest::blocking::Client` with a 15s connect timeout and 20-minute overall timeout.
2. **UI looked frozen during the compute-only phase:** once a model finishes downloading, `enable_chat` still has real work left (loading the model, embedding ~1132 chunks) with no download-progress bytes to report — the progress bar/label just sat stale, indistinguishable from actually being stuck. **Fixed:** added a `chat-status` event emitted before each compute phase, decoupled from the byte-progress `model-download-progress` event.
3. **Silent permission failure on file-open:** `opener:allow-open-path` was granted but with no `scope` — Tauri's ACL denies-by-default even with the permission listed, so every open attempt failed with "Not allowed to open path X," silently, because the JS click handler had no `.catch()`. **Fixed both ends:** added `"allow": [{ "path": "$HOME/**" }]` to the capability, and added error surfacing (`alert(...)` on rejection) so any future permission/IO failure is visible instead of silent.
4. **Debug-build slowness looked like a hang:** see §8's dev-mode note — a legitimate ~minutes-long debug-profile compute phase was initially mistaken for a stuck process. Diagnosed via `ps`/`lsof` (99% CPU, zero open network connections — ruled out a network hang, pointed at unoptimized compute instead) before concluding it needed `--release`, not a code fix.
5. **Mutex held across expensive computation → concurrent calls block, reads as "stuck loading forever":** `enable_chat`, `related_docs`, and `write_answer` all locked `embedding_model`/`chunk_embeddings` and held the lock for the *entire* duration of the embedding computation (`build_chunk_embeddings`, `top_related`'s `embed()` call), not just the brief moment of reading the value out. A second call touching the same lock (e.g. re-selecting AI Search, or `chat_availability` firing while `enable_chat` was still running) blocked waiting on it — with a 27-second `enable_chat` call observed live, this read as a permanent hang rather than a normal wait. **Fixed:** wrapped both fields in `Arc` (`Mutex<Option<Arc<EmbeddingModel>>>`, `Mutex<Arc<Vec<ChunkEmbedding>>>`) so every call site clones the `Arc` and drops the lock immediately, before doing any real work — the lock is now only ever held for a pointer clone, never across computation. General lesson for this codebase: never hold a `Mutex` guard across an `await`-equivalent or a slow synchronous call — clone what you need out from under the lock first.
6. **Real UI freeze during embedding computation, silently swallowing every loading-indicator design tried:** three different loading-UI implementations (a progress bar nested in the panel, a `position: fixed` overlay, a spinner nested in the panel) all failed identically — the indicator's `classList` change demonstrably executed (confirmed via `console.log` and `tracing::info!` on both sides, ruling out a JS/Rust logic bug) but nothing ever appeared on screen. Root cause, per Zac's own diagnosis: the CPU-heavy embedding computation starves the webview's render thread badly enough that a DOM mutation made *immediately before* the blocking `invoke()` call never gets painted — the freeze hits before the browser's next paint cycle fires. This wasn't a CSS/layout bug at all; every DOM-structure change made while chasing it was solving a non-problem. **Fixed:** force a real paint to commit before starting the heavy work — `await new Promise(r => requestAnimationFrame(() => requestAnimationFrame(r)))` between showing the loading state and calling `invoke("enable_chat")`. Double-rAF (not a single rAF, not `setTimeout`) is the standard technique for "block until the browser has definitely painted the current frame." General lesson: if a DOM update provably runs (via logging) but never renders, suspect a starved render thread before suspecting the DOM/CSS — and diagnose via devtools console + `tracing`, not by redesigning the markup.
7. **Raw-folder auto-detect confidently found the wrong folder** (§6) — built on the same shared-OneDrive-root helper used for the vault and inbox, so it always found the *shared team* `raw/` folder, even though the raw badge is meant to trigger `/wiki-builder`, the *personal* skill scanning a completely different path. Caught live: Zac noticed the auto-selected folder didn't match his actual personal raw notes. The two paths are genuinely easy to conflate — same folder name, and the shared vault is even symlinked into the personal one for browsing — which is exactly why `wiki-builder`'s own `SKILL.md` calls out the mixup explicitly. **Fixed:** `autodetect_raw` now checks `wiki-builder`'s own hardcoded scan path directly, with no dependency on the OneDrive/shared-root probe at all. General lesson: two features that both auto-detect "a `raw/` folder" aren't necessarily looking for the same folder — check what the *downstream skill* actually scans, not just what the feature is named.
8. **Automatic-generation redesign fired the heavy chat model on every typing pause, not just on submit:** the first cut of the "automatic answer" UI (§8) chained `write_answer` straight off the same 200ms debounce as extractive search. That's fine for extractive (cheap, near-instant) but generation is CPU-heavy enough to freeze the render thread for its full duration (same class of issue as #6 above) — so it fired, and froze the UI, on every natural mid-sentence typing pause, not just when the user finished asking. Caught live: Zac reported the app locking up after typing only "what " of a longer question. **Fixed:** split the two triggers — extractive search (`related_docs`) stays on the debounce; generation (`write_answer`) only fires on explicit submit (Enter key or the Ask button). General lesson: "automatic" and "on every debounce tick" aren't the same thing once one of the two chained operations is expensive — a debounce that's safe for a cheap operation isn't automatically safe for a heavy one chained after it.
9. **`sysinfo::System::available_memory()` returns a flat `0` on macOS**, confirmed via a live diagnostic test on an 18GB Mac using ~15GB (`total_memory` correct at 19.33GB, `available_memory` exactly `0`, `free_memory` a real-but-misleadingly-low 0.22GB). This is a known sysinfo/macOS gap — it undercounts reclaimable inactive/purgeable pages that `vm_stat` and Activity Monitor both count as available. The low-RAM safety net (§8) built on `available_memory()` therefore fired on *every* query regardless of actual headroom. Caught live: Zac got "Not enough free memory" on a normal, otherwise-idle Mac. **Fixed:** use `total_memory() - used_memory()` instead — confirmed against `vm_stat` to track real availability (~4.16GB on this machine), and well-supported cross-platform. General lesson: don't trust a systems-info crate's cross-platform API surface uniformly — verify the specific method against ground truth (`vm_stat`, Activity Monitor, Task Manager) on each target OS before gating real functionality on it.
10. **Small model drifts into a fabricated new conversation turn, written as plain text, not caught by stopping at the `<|im_end|>`/`<|im_start|>` control tokens:** live repro on a real weak-retrieval query ("How do I enable rate validation?") showed `generate_answer` producing a real, coherent answer and then continuing to generate past it — literally decoding the text `"\n\nQuestion: <invented question>"` — because the model never actually sampled the `<|im_start|>` token for it, just wrote the string "Question:" as ordinary vocabulary. Adding `<|im_start|>` as an additional stop-token condition (kept as cheap insurance) did **not** fix this, since token-level stopping can't catch a drift expressed as plain decoded text. **Fixed:** `truncate_at_fabricated_turn` post-processes the decoded string, cutting at the first `\nQuestion:`/`\nUser:`/`\nQ:` marker. Also separately observed on other weak-retrieval queries: the model sometimes just echoes the question verbatim instead of answering or declining — caught with a narrow exact-normalized-match check (not general low-quality-answer detection) that swaps in a plain "couldn't generate a grounded answer" message. Both are small-model-capability limits, not code bugs to eliminate entirely — the fixes bound the damage a user sees, they don't make the 0.5B model reliably good at every query.
11. **Generation wasn't actually reproducible across app launches — the real root cause behind #10's variety of symptoms:** after shipping #10's fixes, Zac hit a *third*, differently-shaped variant of the same underlying problem on the exact same query ("Questions: How do you enable rate validation?" — no leading newline, plural "Questions", so neither the truncation markers nor the echo-normalize check caught it). Attempting to repro it against the real vault gave a *third, different-again* answer on each of several separate process runs — for the identical query, identical retrieved context, identical fixed sampling seed, and pure greedy (`ArgMax`) decoding, which should be fully deterministic. Root cause: with the thread-pool cap at >1 thread, rayon's parallel float reduction inside gemm's matmul doesn't guarantee a fixed summation order across runs (a known rayon+floating-point caveat — work-stealing means which worker's partial sum lands where isn't pinned to a static schedule), so tiny rounding differences at some token step tip a greedy argmax pick a different way, and the entire rest of the decode diverges from there (small-model decoding is chaotic in this sense). **Fixed:** dropped the thread cap from 2 to 1 (§8) — confirmed via a repeated same-process test (identical query run twice back to back) that 1-thread generation is now byte-for-byte deterministic. This is the more fundamental fix underneath #10's point patches: those patches still matter for genuinely bad model outputs, but before this fix, *which* bad (or good) output you got for a given query was itself random per launch, which made every prior fix impossible to verify with real confidence — a repro that "worked" once could just as easily have been luck. General lesson for this codebase: never assume a fixed-seed, argmax/greedy decode path is deterministic just because the sampler has no randomness in it — the matmul underneath can still introduce real nondeterminism once more than one thread is involved, and that's worth checking explicitly (rerun the same input twice) before trusting any single repro as conclusive.

## 12. Known risks / open items

1. File-watcher robustness against OneDrive sync behavior (partial writes, transient lock files) is defensive-by-design (skip-on-error, filter `~$*`) but was only exercised by real ambient vault activity during verification on Mac, not a deliberate edit-while-running stress test, and not yet exercised on Windows at all — worth a dedicated smoke test there.
2. **Auto-updater (§9a) is implemented but not yet verified end-to-end on a real release cycle** — the whole flow (CI signs + publishes `latest.json` → an old build detects it → downloads → installs → relaunches) has not actually been run against a real GitHub Release yet, on either Mac or Windows. Verify before treating it as the collaborator-facing default, not just "the code compiles."
3. **The switch to `tauri-apps/tauri-action` for CI (§9) assumes it avoids the Zscaler-blocked artifact-storage domain** that forced the old manual two-job workflow — reasoned from how the action uploads (direct to the Release-assets API, not through `actions/upload-artifact`), not confirmed by an actual CI run on this network yet. If a release fails with a network error, this is the first thing to check; the old manual build/upload/publish steps are the documented fallback (§9a's plan).
4. Full-rewalk-on-any-change indexing (§3) assumes the vault stays small; revisit if it ever measurably slows down.
5. The `claude://code/new?q=...` badge launch (§6) is verified working end-to-end on Mac (both the raw OS-level `open` call and the app's own permission-scoped `openUrl`) but not yet on Windows — same category of gap as the rest of this list, not expected to differ (Claude Desktop ships for both platforms and URL-scheme registration is standard cross-platform practice) but genuinely untested.
6. `autodetect_raw` (§6, §11 #7) assumes every collaborator's personal Second Brain vault lives at the literal `~/Documents/Claude/Projects/Second Brain/Second Brain Obsidian/raw/` path — true for anyone who followed the standard onboarding (it's `wiki-builder`'s own hardcoded scan target), but if a collaborator's personal setup deviates from that convention, auto-detect will just find nothing and fall back to manual browse, same as today, not silently wrong. Worth confirming this holds across a few real collaborator machines, not just Zac's.
7. The Gatekeeper-quarantine-not-recurring-on-updates reasoning in §9a is plausible but unconfirmed — verify on the first real update cycle before telling collaborators to expect it.
